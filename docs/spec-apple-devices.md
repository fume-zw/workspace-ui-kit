## 1. いまの実態（As-Is）

「API をつないていない」は半分正しく、半分正確ではない。

| つながっているもの | つながっていないもの |
| --- | --- |
| **Supabase**（認証・タスク・予定の読み書き） | Apple Calendar / Reminder / Watch / HealthKit |
| **GitHub Actions → LINE**（朝レポート） | このアプリ独自の REST API（外部クライアント向け） |
| Safari / Chrome で開く **Web アプリ** | App Store の iPhone アプリ・watchOS アプリ |

クライアント分担の現状:

| 端末 | 実態 | できること | できないこと |
| --- | --- | --- | --- |
| **PC** | `/` の 4 ペイン | タスク・サブタスク・イベント・勤務・定期タスクの本拠 | — |
| **iPhone** | Safari 等で `/mobile` | タスク追加、当日の予定閲覧、イベント追加 | タスク完了、勤務追加、ホーム画面アプリ化、通知の公式経路 |
| **Apple Watch** | 未接続 | LINE アプリ経由で朝レポートが届く可能性のみ | 本アプリの予定・タスクを文字盤やカレンダーで見ること、手首で完了すること |

結論: Watch に予定を出すには、**Web 画面を伸ばすだけでは届かない**。Watch は Web アプリを実行できない。iPhone の Safari から Watch へデータを送る API も、Web にはない。

## 2. 目的（To-Be）

手首とポケットで、**今日なにをするか**が分かること。編集の本拠は今どおり PC と iPhone に残す。

| 優先 | 体験 | v1 で目指す到達点 |
| --- | --- | --- |
| P0 | iPhone で今日の予定と期限を見る | `/mobile` を「登録専用」から **当日ハブ** にする |
| P0 | Watch で今日の予定が目に入る | iPhone の **純正カレンダーに購読**し、Watch はそれをミラーする |
| P1 | 期限・開始時刻に気づく | カレンダー予定にアラームを載せ、Watch の純正通知に乗せる |
| P2 | 外出先で完了する | iPhone `/mobile` でタスクを完了。Watch からの完了は v1 対象外 |
| P3 | 文字盤に残数を出す / 手首で完了 | **ネイティブ watchOS アプリ（v2）**。Apple Developer プログラムが必要 |

正本は動かさない。Watch も iPhone も **Supabase の複製表示**であり、予定のマスターを Apple 側に移さない。

---

## 3. 方式の選択（なぜカレンダー購読か）

Watch 連携には大きな分岐が2つある。v1 は **方式 A を正**とする。

| | 方式 A: カレンダー購読（ICS） | 方式 B: ネイティブ iOS + watchOS |
| --- | --- | --- |
| Watch に出るもの | 純正カレンダー・純正通知 | 専用アプリ・コンプリケーション |
| 手首で完了 | できない | できる |
| Apple Developer（年額） | **不要** | **必須** |
| このリポジトリで足りるか | **足りる**（Route Handler + `/mobile`） | 足りない（Swift の別リポジトリ） |
| 同期の速さ | Apple 側の購読更新（目安: 数十分〜数時間） | アプリ実装次第でほぼ即時 |
| 向いていること | 「予定を見る・知らせる」 | 「Watch を入力端末にする」 |

方式 A を正とする理由:

1. 今のアプリは Next.js + Supabase の Web であり、Watch 専用 UI を置く場所がない。
2. 個人1人の稼働ツールなので、まず **見えること・忘れないこと** が価値で、手首完了は後回しにできる。
3. iPhone のカレンダーを購読すれば、Watch のカレンダーは **追加実装なし**で付いてくる。
4. 方式 B は年額と別技術スタックが前提。必要になったら v2 で切り出す（§7）。

方式 A で Watch に届く経路:

```
Supabase（正本）
  → 本アプリが ICS（カレンダーファイル）を配る
  → iPhone のカレンダーが購読
  → Apple Watch のカレンダー / 通知が iPhone をミラー
```

iPhone 上の本アプリ（`/mobile`）は、購読の遅さを補う **即時の閲覧・完了** 担当とする。

## 4. クライアント再定義

既存仕様の「PC = 深い作業 / スマホ = 軽い追加」を、端末役割まで広げて上書きする。

| クライアント | 役割 | 読み | 書き |
| --- | --- | --- | --- |
| PC `/` | 本拠。プロジェクト・サブタスク・勤務一括・定期ルール | 全部 | 全部 |
| iPhone `/mobile` | **当日ハブ**。見る・足す・完了する | 当日〜数日のタスクと予定 | タスク追加 / タスク完了 / イベント追加 |
| Apple Watch | **閲覧と通知のみ**（純正カレンダー経由） | 方式 A が配った予定 | なし（v1） |
| 自動報告ツール | 朝の要約（LINE） | 期限フィルタ済みタスク | なし |

`/mobile` の v1 入力（タイトル・期限・ステータス・プロジェクト）は残す。予定閲覧とイベント追加（現行）も残す。足りないのは **完了** と **Watch への出口** である。

## 5. 機能要件

### 5.1 iPhone（`/mobile`）

| ID | 要件 | 優先 | 現状 |
| --- | --- | --- | --- |
| M-1 | ログイン済みなら、起動時の主画面は **選んだ日の予定**（タスク追加が初期画面ではない） | P0 | 未。初期タブはタスク追加 |
| M-2 | 選択日の統合アジェンダ（期限タスク・イベント・勤務）を表示する。PC Pane 4 と同じ種類の見分け（タスク / イベント / 勤務） | P0 | 実装済み（`MobileScheduleView`） |
| M-3 | その場でタスクを追加できる | P0 | 実装済み |
| M-4 | その場でイベントを追加できる | P0 | 実装済み |
| M-5 | 未完了タスクを **完了** にできる（ステータス `done`） | P0 | 未 |
| M-6 | 「カレンダーに出す」設定。購読用 URL の表示、再発行、無効化、iPhone への追加手順 | P0 | 未 |
| M-7 | ホーム画面に追加できる（Web クリップ / マニフェスト）。フルの App Store アプリにはしない | P1 | 未 |
| M-8 | 勤務の一括追加・定期ルール編集・サブタスク編集は iPhone ではやらない。PC へ誘導する | P0 | 現行どおりで可 |

勤務追加を iPhone に足すことは、この修正の対象外とする（情報量とダイアログが PC 前提のため）。

### 5.2 Apple Watch（方式 A）

| ID | 要件 | 優先 | 実現手段 |
| --- | --- | --- | --- |
| W-1 | 今日のイベント・勤務が Watch のカレンダーに見える | P0 | iPhone が ICS を購読していれば自動 |
| W-2 | 期限つき未完了タスクが、期限日の予定として見える | P0 | ICS に終日イベントとして載せる |
| W-3 | 開始時刻つき予定は、開始前に Watch が知らせる | P1 | ICS の `VALARM` |
| W-4 | 期限タスクは期限日朝に知らせる | P1 | ICS の `VALARM`（既定 **当日 08:00 JST**。変更可） |
| W-5 | 文字盤コンプリケーションに「残タスク数」を出す | — | **v1 対象外**（ネイティブ必須） |
| W-6 | 手首のタップでタスク完了 | — | **v1 対象外** |

Watch 側に本アプリの画面は作らない。ユーザー操作は「iPhone のカレンダーにアカウント（購読）を1回追加する」だけとする。

### 5.3 カレンダーフィード（本アプリが新しく足す API）

これが「Apple 向けに初めて足す API」である。Next.js の Route Handler で ICS を返す。外部の汎用 REST は公開しない。

| ID | 要件 |
| --- | --- |
| F-1 | `GET /api/calendar/[token].ics` が `text/calendar` を返す |
| F-2 | トークンはユーザーごとに1つ。URL を知っている人だけが読める（Cookie ログインは使わない。カレンダーアプリがログイン画面を通せないため） |
| F-3 | `/mobile` からトークンを発行・再発行・無効化できる。再発行したら古い URL は即無効 |
| F-4 | HTTPS の本番 URL だけを正規の購読先とする |
| F-5 | フィードは **読み取り専用**。Apple カレンダー上で予定を動かしても Supabase には戻さない |
| F-6 | 同じ予定は安定した `UID` を持ち、更新のたびに上書きされる（毎回別予定として増えない） |
| F-7 | タイムゾーンは既存どおり **JST 固定** |

掲載ルール（仮確定）:

| 元データ | ICS 上の形 | 載せない条件 |
| --- | --- | --- |
| イベント（`schedule_entries.kind = event`） | 時刻つき、または終日 | なし（過去も含める。履歴を消さない方針に合わせる） |
| 勤務・時間ブロック | 時刻つき（夜勤の日跨ぎ可） | アーカイブ済みラベルでも、既存の勤務行は出す |
| 勤務・終日マーカー（休み等） | 終日 | なし |
| 期限つきタスク | 期限日の終日。タイトルはタスク名 | `done`、または `due_date` なし |
| 定期タスク各回 | 通常タスクと同じ（期限日の終日） | 上に同じ |
| サブタスク | 出さない | — |

タイトルの見分け（仮確定）:

- イベント: `会議 週報` のように **ラベル名 + タイトル**（ラベルなしならタイトルのみ）
- 勤務: 勤務ラベル名（個別タイトルがあればそれを優先）
- タスク: `タスク 週報提出` のように接頭辞 `タスク` を付ける（カレンダー上で予定と混ざらないようにする）

アラーム（仮確定）:

- 時刻つき予定: 開始 **15 分前**
- 終日の勤務マーカー: なし（休みを毎朝鳴らさない）
- 期限タスク: 当日 **08:00 JST**

フィードの期間: **過去 30 日〜未来 90 日**。無制限に出すと購読が重い。定期タスクのローリング生成（先 8 週）より未来は、生成されていない各回は出ない（既存の生成ルールに従う）。

### 5.4 データ・セキュリティ

- 正本は Supabase。ICS は投影。
- トークンは推測困難なランダム値。GitHub やスクリーンショットに出さない。
- 購読 URL が漏れたら再発行する（旧 URL 無効）。
- RLS と同じく、トークンの所有者の行だけを載せる。
- 方式 A は Hobby / 無料枠のままで実装できる。Watch 連携のために有料プランは必須にしない。

## 6. 非機能・運用

| 項目 | 要件 |
| --- | --- |
| 即時性 | `/mobile` と PC は保存後すぐ反映。Watch / 純正カレンダーは購読更新待ち（即時を約束しない） |
| 競合 | 従来どおり最後の書き込み優先。カレンダー側からの書き戻しが無いので、二重編集は起きない |
| 可用性 | 本番が止まるとフィードも止まる。復旧は Vercel 再デプロイ / Supabase Resume（別途運用メモ） |
| 説明 | `/mobile` の設定に「Watch には数時間遅れることがある。今すぐ見るならこの画面」と書く |
| テスト | ICS の UID・期間フィルタ・`done` 除外・トークン無効化を単体テストする。実機の購読確認は手動 |

## 7. v2（ネイティブ）に送るもの

次を満たしたら方式 B を検討する。v1 の ICS は残してよい（カレンダー連携はネイティブでも有用）。

- Watch の文字盤に残数を出したい
- 手首で完了したい
- カレンダー更新の遅れが運用上つらい
- Apple Developer プログラムに加入する意思がある

v2 の骨格（実装しない。置き場だけ決める）:

- 別リポジトリの SwiftUI。Web の 4 ペインは移植しない
- 認証は Supabase Auth（メール + パスワード）をネイティブ SDK で行う
- 読み書きは Supabase の REST/RPC。この Next.js に巨大な JSON API は増やさない
- Watch は「今日の件数・直近3件・完了トグル」に限定する

## 10. 受け入れ条件（v1）

1. iPhone のカレンダーに購読 URL を追加すると、本アプリのイベント・勤務・期限つき未完了タスクがカレンダーに出る。
2. 同じ iPhone にペアリングした Apple Watch のカレンダーに、同じ予定が見える。
3. 時刻つき予定の開始前、および期限タスクの当日朝に、Watch または iPhone の純正通知が来る（アラームを無効にしない限り）。
4. `/mobile` でタスクを完了すると、次回のフィード更新以降その終日予定は消える（即時ではない）。
5. トークンを再発行すると、古い URL は 404 または 401 になり、他人に漏れた購読を止められる。
6. PC の 4 ペインと日次 LINE レポートの既存動作を壊さない。
