## 0. 確定した判断

2026-08-20 の回答で、次を確定する。

| # | 質問 | 確定 |
| --- | --- | --- |
| 1 | Watch の音声はショートカットでよいか。プロジェクト（システム / 生化学免疫 等）は音声で分けるか | **ショートカットでよい。プロジェクトは音声では分けない。** すべて **未割当**。あとから iPhone または Windows ブラウザで割当・編集する |
| 2 | 音声で入れるもの | **「スケジュールに入れて」「タスクに入れて」で言い分ける。** 言わなければ開始時刻があれば予定、なければタスク。タスクは未割当。期限は言ったときだけ |
| 3 | Google / Apple カレンダー | **まだ使っていない。検討段階。** 使うときはおすすめどおり、同じ ICS を購読する（Google Calendar API 書き込みはしない）。**今すぐ購読しなくてよい** |
| 4 | 時刻つきの会議 | **入れる。** アプリのスケジュールは既に何時からを持てる。音声の「何月何日の何時から会議」はイベントとして保存 |

## 1. なぜカレンダーだけでは足りないか

カレンダー（Google も Apple も）が得意なのは **時刻の枠** である。このアプリが既に持っているものは、枠だけでは表せない。

| このアプリにあるもの | カレンダーでの扱い | 結果 |
| --- | --- | --- |
| イベント・勤務の時間ブロック | 予定として自然 | 連携向き（ICS を足したあと） |
| 休みなどの終日マーカー | 終日予定で足りる | 連携向き |
| 期限だけあるタスク（時刻なし） | 終日にするか、リマインダーに逃がすかで毎回迷う | ここで崩れる |
| 未着手 / 進行中 / 至急 / 保留 / 完了 | カレンダーに状態がない | 進捗が置けない |
| プロジェクト・未割当 | カレンダーに軸がない | 分けられない。音声でも分けない |
| サブタスク | 載らない | — |
| 定期タスク（各回を独立にずらす） | カレンダーの繰り返しと意味が違う | 1回だけ変更が壊れる |
| Windows と iPhone と Watch | Google は Windows に強い。Apple リマインダーは Windows に弱い。Watch は Apple 側に寄る | 正本が分裂する |

今あるアプリは、すでに正本の形をしている。ゼロから作り直さず、**音声入口**と（必要になったら）**カレンダーへの投影**を足す。

## 2. 目指す役割分担

```
 Apple Watch  音声「追加」── POST /api/inbox ──┐
  （「スケジュールに入れて」/「タスクに入れて」）     │
  （予定確認は、ICS を使い始めたら純正カレンダー）      │
                                                       ▼
                                              自作アプリ（正本・Supabase）
                                                Windows `/`     … 確認・編集・追加・プロジェクト割当
                                                iPhone `/mobile` … 確認・編集・追加・プロジェクト割当
                                                       │
                              検討後に足す ICS 購読     │
                       Google カレンダー / Apple カレンダー
                       Apple Watch は Apple をミラー
```

| 置くもの | 置き場 | 置かないもの |
| --- | --- | --- |
| タスクの正本 | 自作アプリ | Google ToDo / Apple リマインダー |
| 予定の正本 | 自作アプリ | カレンダー上で作った予定 |
| 音声で入ったタスク | 未割当。期限は発話にあれば付ける | 音声でのプロジェクト判定 |
| 音声で入った会議 | 時刻つきイベント（終了省略時は1時間）。時刻なしでスケジュール行き先なら終日 | 音声での勤務・繰り返しテンプレ |
| 予定の見え方 | 使う段階で ICS を Google と Apple が購読 | 今すぐの必須セットアップ |

原則: **追加・編集は自作アプリ。** カレンダー側で足した予定はアプリに戻さない。

### 3.3 Apple Watch

専用 Watch アプリは作らない。

| ID | 要件 | 優先 | 実現手段 |
| --- | --- | --- | --- |
| W-3 | 音声でタスクまたは時刻つき予定を追加する | **P0（先にやる）** | Siri ショートカット → `POST /api/inbox` |
| W-1 | 今日のイベント・勤務をカレンダーで確認する | P1（ICS を使い始めてから） | Apple 純正カレンダー |
| W-2 | 期限つき未完了タスクを期限日の予定として見る | P1 | 同じ ICS |
| W-4 | 開始前・期限朝の通知 | P1 | ICS の `VALARM` |
| W-5 | 手首で完了 / 文字盤の残数 / 勤務の音声追加 | — | v2 |

PC のスケジュール機能は **すでに時刻を持てる**。音声は **先に言い分け、無ければ推定** する。

- 「**スケジュールに入れて**」「**予定に入れて**」→ 必ずイベント
- 「**タスクに入れて**」→ 必ずタスク（未割当）
- どちらも言わない → 開始時刻があればイベント、なければタスク

音声追加（W-3）の操作:

1. iPhone にショートカット「追加」を1つ置く（初回だけ。名前は変更可）。
2. Watch で「Hey Siri、追加」。
3. 一文を話す。行き先を言うなら文の前後どちらでもよい。
4. サーバーが予定かタスクかを分けて保存する。タスクならプロジェクトは見ない（常に未割当）。
5. Watch に「予定に入れました」または「タスクに入れました」と返す。

例:

| 発話 | 入るもの |
| --- | --- |
| `試薬発注をタスクに入れて` | 未割当タスク・期限なし |
| `明日まで週報、タスクに入れて` | 未割当タスク・期限は明日 |
| `8月25日の14時から会議をスケジュールに入れて` | イベント 8/25 14:00–15:00 |
| `明日の会議を予定に入れて` | **終日**イベント（時刻なし） |
| `8月25日の14時から会議`（言い分けなし） | イベント（開始時刻があるので推定） |
| `試薬発注`（言い分けなし） | 未割当タスク |

制約:

- iPhone が近く、ネットに出ていること。
- Siri がショートカット名を聞き取ること。
- プロジェクト名はタイトルに残し、割当には使わない。
- 勤務（当直・採血当番）は音声では作らない。PC のラベル一括のまま。
- 今すぐ直すのは iPhone `/mobile` か Windows。

## 4. 音声追加 API（先に実装する）

| ID | 要件 |
| --- | --- |
| I-1 | `POST /api/inbox`。JSON `{ "text": "…" }`。成功時に `{ ok, kind: "task" \| "event", title, when, speak, id }` を返す |
| I-2 | Cookie は使わない。環境変数 `INBOX_TOKEN`（128bit 以上）を `Authorization: Bearer` で送る。書き込みは `SUPABASE_SERVICE_ROLE_KEY` + 固定 `INBOX_USER_ID`。middleware は **`/api/inbox` だけ**公開。ICS 用の鍵とは別（R-2） |
| I-3 | `text` は前後空白を除き 1〜200 文字。空なら 400 |
| I-4 | 行き先は §4.1。明示があればそれを優先。無ければ開始時刻の有無で推定 |
| I-5 | タスクのとき: そのユーザーの `not_started` の **`status_id`**、`project_id = null`。期限は §4.2。取れなくても追加は成功 |
| I-6 | イベントのとき: `event_label_id = null`。開始時刻があれば `allDay = false`（終了省略時は開始+1時間）。**時刻が無ければ `allDay = true`**（その日の終日） |
| I-7 | レート制限（目安: トークンあたり 30 件/時） |
| I-8 | `/mobile` にショートカット手順を書く（トークンは画面に出さない） |
| I-9 | 同一正規化文言を 60 秒以内に再送しても新規行は作らない。成功読み上げは「『週報』をタスクに入れました」。失敗は短い日本語 |

Route Handler にする。分解ルールは単体テストする。

### 4.1 タスクか予定か（言い分けが最優先）

ショートカットは質問を増やさない。**一文をサーバーが分解する。** 基準は API 実行時点の **Asia/Tokyo**。

**1. 明示（これがあれば推定しない）**

| 発話に含まれる語 | 作るもの |
| --- | --- |
| `スケジュールに入れて` / `スケジュールを入れて` / `予定に入れて` / `予定を入れて` / それぞれの「入れといて」 | **イベント** |
| `タスクに入れて` / `タスクを入れて` / `タスクに入れといて` / `タスクにして` | **タスク** |

語はタイトルから落とす。両方言ったときは **あとに出た方** を使う。

明示したあとの中身:

| 行き先 | 日付 | 時刻 | 結果 |
| --- | --- | --- | --- |
| スケジュール | あり | あり | その日時のイベント。終了なしなら +1時間 |
| スケジュール | あり | なし | **その日の終日イベント** |
| スケジュール | なし | あり | 日付は §4.2（今日か明日） |
| スケジュール | なし | なし | **今日の終日イベント**。タイトルだけ残る |
| タスク | 任意 | あっても無視 | 未割当タスク。日付があれば期限。時刻は保存しない |

**2. 明示が無いときの推定（これまでどおり）**

| 条件 | 作るもの |
| --- | --- |
| 開始時刻がある（`から` / `時に` / 開始の `○時`） | イベント |
| それ以外 | タスク |

「15時まで週報」のように終わる時刻だけで「から」も言い分けも無いものはタスク。日付が取れたらその日を期限にする。会議にしたいときは「スケジュールに入れて」か「15時から」を付ける。

### 4.2 日付の取り方（タスクの期限 / イベントの日）

認識する日付:

- `今日` / `明日` / `明後日`
- `今週の月曜` 〜 `日曜`、`来週の月曜` 〜 `日曜`
- 単独の曜日 = 基準日以降で最初のその曜日（今日が該当なら今日）
- `M月D日` / `YYYY年M月D日` / `D日`（`D日` は基準日以降の今月、過ぎていれば翌月）

タスクに日付があれば `due_date` にする。「まで」「までに」「期限」は **無くてよい**（付いていればタイトルから落とす）。日付が複数なら最後の1つ。

「昨日」は使わない。プロジェクト名の辞書マッチはしない。

`M月D日` が基準日より前なら **翌年**。`D日` だけなら基準日以降の今月、過ぎていれば翌月。

日付が無く開始時刻だけ（`14時から会議`）のとき: その時刻がまだ来ていなければ **今日**、過ぎていれば **明日**。

### 4.3 時刻の取り方（イベント）

認識する開始・終了:

- `N時` / `N時M分` / `N時半`（半 = 30分）/ `N:MM`
- `午前` / `午後` / `朝` / `夜`（夜7時 = 19:00）
- 午前午後がなく 1〜6 時のときは **午後とみなして +12h**（7〜23 はそのまま）
- `正午` = 12:00
- `A時からB時` / `A時からB時まで` / `A時からB時間`（B時間は開始からの長さ）

終了が開始以前なら、終了は翌日（夜をまたぐ会議）。**行き先がスケジュールなのに開始が取れない**ときは終日イベント（タスクに落とさない）。行き先が無いかタスクのときに開始が取れなければタスク。開始だけ取れて終了が壊れていれば開始+1時間。

タイトルは、日付・時刻・行き先の語・`から` / `まで` / `の` を除いた残り。空ならイベントは **`予定`**、タスクは **`タスク`**。

## 5. カレンダー連携（検討段階・おすすめどおり ICS）

まだ Google / Apple カレンダーは使っていない。**音声 inbox と iPhone 編集が先。** ICS は「Watch や外部カレンダーで予定を見たくなったとき」に足す。

使うときの方式（確定）: **同じ読み取り専用 ICS を、使いたい側が購読する。** Google Calendar API で書き込まない。購読は Google だけ、Apple だけ、両方、のいずれでもよい。両方だと予定が二重に見えることがあるので、手順に注意を書く。

| ID | 要件 |
| --- | --- |
| F-1 | `GET /api/calendar/[token].ics` が `text/calendar` を返す |
| F-2 | トークンはユーザーごと。URL 自体が鍵 |
| F-3 | `/mobile` と PC から発行・再発行・無効化 |
| F-4 | Google（URL で追加）と Apple（購読カレンダー）の手順を画面に書く |
| F-5 | 読み取り専用。カレンダー上で動かしても Supabase に戻さない |
| F-6 | 安定した `UID` |
| F-7 | **JST 固定** |

掲載ルール:

| 元データ | ICS 上の形 | 載せない条件 |
| --- | --- | --- |
| イベント | 時刻つき、または終日 | なし（過去も出す） |
| 勤務・時間ブロック | 時刻つき（夜勤の日跨ぎ可） | なし |
| 勤務・終日マーカー | 終日 | なし |
| 期限つきタスク | 期限日の終日。接頭辞 `タスク` | `done`、または期限なし |
| 定期タスク各回 | 上に同じ | 上に同じ |
| サブタスク | 出さない | — |
| 音声で入った期限なしタスク | 出さない | 期限を付けてから載る |

タイトル: イベントは `ラベル タイトル`、勤務はラベル名、タスクは `タスク タイトル`。

アラーム: 時刻つきは開始15分前。期限タスクは当日 08:00 JST。終日の休みは鳴らさない。

期間: **過去 30 日〜未来 90 日**。

## 6. データ・運用

- 正本は Supabase。
- **inbox 鍵と ICS 鍵は別。** inbox を再発行してもカレンダー購読は止まらない。ICS を再発行してもショートカットは止まらない。
- トークンは推測困難。漏れたら再発行。
- 即時性: inbox / PC / iPhone はすぐ DB に乗る。**Realtime は使わない。** 開き直す、フォアグラウンドに戻る、または再読み込みで再取得する。開きっぱなしは手動更新。
- カレンダー購読は数十分〜数時間遅れうる（使い始めてから）。
- 音声の成功確認はショートカットの返答で足りる。
- Watch 連携のために有料プランは必須にしない。
- 本番では Vercel に `INBOX_TOKEN` / `INBOX_USER_ID` / `SUPABASE_SERVICE_ROLE_KEY` を置く。

## 7. v2 に送るもの

v1 でやる「スケジュールに入れて / タスクに入れて」「何時から会議」「時刻なしの終日予定」「未割当に入れる」は v2 に送らない。

- 手首で完了、文字盤に残数
- カレンダーの遅れがつらい、ショートカットの聞き取りがストレス
- ネイティブ watchOS（Apple Developer プログラムが必要）

## 10. 受け入れ条件

**フェーズ 1〜2（カレンダーなしでも達成）**

1. Watch の Siri「追加」で一文を入れると、Windows / iPhone にすぐ見える。
2. 「週報をタスクに入れて」は未割当タスク。「8月25日の14時から会議をスケジュールに入れて」は 14:00–15:00 のイベント。「明日の会議を予定に入れて」は終日イベント。
3. 言い分けが無い「14時から会議」は予定、「試薬発注」はタスク（推定）。
4. 「システム」「生化学免疫」と話してもプロジェクトには入らず、タスクなら未割当のままタイトルに残る。
5. 開始時刻が取れない発話でも落とさない（明示が無ければタスク、スケジュール明示なら終日）。
6. iPhone または Windows で、タスクのプロジェクト割当・期限変更・完了、イベントの時刻編集ができる。
7. 既存の 4 ペインと朝の LINE レポートを壊さない。

**フェーズ 3（ICS を使い始めたら）**

8. 同じ ICS を Google と Apple の片方または両方に購読できる。
9. 期限つき未完了タスクとイベント・勤務がカレンダーに出る。期限なしの音声タスクは出ない。
10. **ICS トークン**の再発行で古い購読は止まる。ショートカット（inbox トークン）は止まらない。inbox トークン再発行では逆。

## 12. シニアレビュー（2026-08-20）

仕様変更の積み残しを、仕様書と現行コードの両方からレビューした。**方向性は妥当。** 推奨 R-1〜R-10 は同日の回答で **確定**し、フェーズ 1〜2 に入れた。

### 12.1 実装前に決める（P0）— **確定**（推奨どおり採用）

| ID | 不足 | 確定 |
| --- | --- | --- |
| R-1 | inbox の認証（トークン置き場、ヘッダ、user_id、middleware） | 1人用。環境変数 `INBOX_TOKEN`（128bit 以上）。`Authorization: Bearer`。`/api/inbox` だけ middleware 公開。書き込みは service role + 固定 `INBOX_USER_ID`。現行 RLS の `auth.uid()` はショートカットに使えない |
| R-2 | inbox 鍵と ICS 鍵は同じか | **別鍵**。inbox 再発行はショートカットだけ止める。ICS 再発行は購読だけ止める |
| R-3 | 期限なし未割当が `/mobile` に出ない | `/mobile` の **未割当リスト**。日付を勝手に「今日」にはしない |
| R-4 | 「すぐ見える」 | Realtime は使わない。アプリを開き直す / フォアグラウンド復帰 / 再読み込みで再取得 |
| R-5 | 「8月25日の週報をタスクに入れて」（まで無し） | **日付があれば期限にする。** 「まで」は無くてよい |
| R-6 | `15時まで` と `15時から` の衝突 | 明示行き先 → `A時からB時` → `から`/`時に` → `まで` だけは開始に使わない → 残り `○時` は開始 |
| R-7 | `1月1日` が今年の過去になる | 基準日より前の `M月D日` は **翌年** |
| R-8 | 失敗時の Watch 読み上げ、二重送信 | 成功は「『週報』をタスクに入れました」。失敗は短い日本語。同一文言 60 秒以内は新規にしない |
| R-9 | `status = not_started` | 正は **そのユーザーの `not_started` の `status_id`**。text 列は無い |
| R-10 | 終日イベントは v1 か v2 か | **v1 でやる**（「明日の会議を予定に入れて」） |

### 12.2 あとでよい（P1）

- `/mobile` の編集最小セット（タスク: タイトル/期限/プロジェクト/完了。イベント: タイトル/時刻/終日/削除）
- 全角数字は正規化、漢数字は対象外、未知の日付語は無視して追加成功
- タイトルから落とすのは日付・時刻・行き先フレーズだけ（単独の「の」は残す）
- `朝6時` は 06:00。修飾が無い 1〜6 時だけ +12h
- 勤務語（当直・休み）は拒否せず、普通のイベント/タスクのタイトルとして残す
- ICS の UID・窓・VALARM はフェーズ3着手時
- LINE レポートは現状維持（期限なし音声タスクは朝報に載らない）

### 12.3 仕様書の矛盾（直した）

- §7「終日予定は v2」と §4・受け入れの終日 v1 → **R-10 で v1。§7 から削除済み**
- 本体 `spec-task-workspace.md` の Watch 行 → 音声追加を先、カレンダー閲覧は ICS 後
- 受け入れフェーズ3の番号 → 8 から振り直し
- I-5 の `status = not_started` → `status_id`
- inbox と ICS の「トークン」を同一視していた受け入れ条件 → R-2

### 12.4 コード側で既に決まっていること（仕様に書き戻す）

- 終日は `buildAllDayEventRange`（JST 00:00–23:59）
- 時刻つきは `buildTimedEventRange`。日跨ぎは既存ヘルパー
- 「今日」は API の Asia/Tokyo。`todayDateKey()`（ブラウザローカル）は inbox で使わない
- 音声は `kind: "event"` のみ。`insertShiftsBulk` / 定期テンプレは呼ばない
- フェーズ1で 4ペイン・既存 RLS ポリシー・モバイル追加フォームの破壊はしない。新規 `app/api/inbox/route.ts` と分解テストと middleware の inbox 例外だけ
